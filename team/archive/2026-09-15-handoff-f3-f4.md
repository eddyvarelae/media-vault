# F3 — `copy` exits 0 when a collision leaves a file unarchived

## Framing (read this before the code)

**This is not a defect in the five merged commits.** It is a standing behaviour question
about `copy` generally, and it predates `content-dedupe` by four commits — `--on-collision`
landed in `6dabfdb`, and before F2 `runCopy` had no exit handling after the loop at all.
Collisions have always been reported in the output and have always exited 0.

I described it earlier as "the same blind spot F2 was written to close," which leaned too
far toward defect language. Correcting that here so it isn't carried forward.

## The behaviour

```
$ vault copy diskS S dest --on-collision rename-mtime-year
(1 files SKIPPED — dst path already exists; use --on-collision rename-mtime-year to disambiguate)
Done. Copied 0/0 files, 0 B.
exit 0            manifest rows: 0
```

A source file was not archived, got no manifest row, and the run reported success.
`scripts/nas-tars-copy-all.sh` runs four cards unattended and branches on this status, so a
card can archive nothing and the log says `done`.

## Scope: `len(plan.DstCollisions) > 0` — and that is already the right predicate

The concern raised was that failing on collisions would break the normal
`rename-mtime-year` path, where 831 files in the live archive are collision-renames and 679
of those rescued genuinely distinct footage.

**It doesn't, because `DstCollisions` already excludes every one of those.** In
`internal/scan/scan.go`, the rename is attempted first and a task reaches `DstCollisions`
only if the renamed path *also* exists:

```go
task.DstRel = renameWithMtimeYear(task.DstRel, task.MtimeNs)
if _, again := os.Stat(dstFull); again == nil {
    p.DstCollisions = append(p.DstCollisions, task)   // renamed AND still blocked
}
// otherwise falls through to ToCopy
```

Confirmed both ways: a successful rename lands in `ToCopy` and the run reports
`Dst collisions: 0`; forcing a `DstCollisions` entry required pre-creating **both**
`only.mov` and `only_2026.mov`. So a run that renames 200 files and archives them all
reports zero collisions and passes F3 untouched.

`len(plan.DstCollisions) > 0` already means *"the collision policy had its say and the file
still is not archived."* That is exactly the condition to fail on. No new predicate needed.

## Decision on the narrow case — recorded, not open

**Case:** with `--dedupe-content`, a collision-skipped file whose identical twin in the same
source gets copied for real (a consequence of the R2-1 fix). The *bytes* reach the archive;
what is missing is a manifest row for the skipped path.

**Decision: it still fails the run.** Agreed between reviewer and dev on 2026-09-15.

Reasoning, so this is not re-litigated:

1. `copy` cannot distinguish "this content landed under another name" from "this file was
   dropped" unless `--dedupe-content` is on. Making the exit code depend on whether that
   flag was passed would be surprising — the same source, same destination, same collision
   would pass or fail based on an unrelated flag.
2. The missing manifest row *is itself* the problem. This branch already established that
   precedent: round-1 finding 2 rejected unrecorded dedupes precisely because an auditable
   archive must not silently hold content it has no row for. A collision-skipped path is the
   same gap arriving by a different route.

**Alternative considered and rejected:** fail only when the collided content is not archived
elsewhere. Rejected for (1) above, and because the provenance gap remains either way.

## Implementation

`runCopy` in `cmd/vault/main.go`, the block F2 added after the summary line. Extend the
condition and the message:

```go
if failed > 0 || orphaned > 0 || len(plan.DstCollisions) > 0 {
    os.Exit(1)
}
```

Report collisions in the `INCOMPLETE:` line alongside the existing counts, so the log says
which of the three reasons fired.

Leave exiting 0:
- `--dry-run`, even when it predicts collisions — it is informational and returns earlier.
- `Nothing to copy. Manifest is up to date.` — unreachable with collisions present, since
  that early return already requires `len(plan.DstCollisions) == 0`.
- The interrupt path, which already exits 1 on its own.

## Done when

- A run with an unresolved collision exits 1 and names collisions in `INCOMPLETE:`.
- A run under `rename-mtime-year` where every rename succeeds exits 0.
- Fully successful, no-op, and dry-run runs still exit 0.
- `failed`/`orphaned` cases from F2 still exit 1 and still say which fired.
- `nas-tars-copy-all.sh` logs `FAILED` for a card whose files were all collision-skipped.

# F4 — `verify --only-unverified`: yes, its own round

Answering the question directly: **worth doing, as a separate round, and it can run in
parallel with F3** — F3 is confined to `runCopy`, F4 to `runVerify` + `internal/verify` +
`internal/manifest`. Different functions in `main.go`, so conflicts are unlikely. If you'd
rather be safe, land F3 first; it is the smaller change.

## The problem is real

`verify.Run` calls `m.ListByDisk(disk)` and hashes every row returned, with no status
filter. There is no way to verify only what is new. Promoting the 195 `copied` rows means
re-hashing the whole disk — 3.3 TiB, ~11 hours, to certify 1.1 GiB of new material. That
cost is also what currently stands between the live archive and `--dedupe-content` doing
anything at all, since dedupe matches only `verified` rows.

## Design constraints I'd want held

1. **Filter in SQL, not in Go.** A `ListByDiskUnverified` (or a status predicate on
   `ListByDisk`) with `WHERE source_disk = ? AND status != 'verified'`. `idx_files_disk`
   covers it.
2. **Include every non-verified status, not just `copied`.** The vocabulary is `copied`,
   `verified`, `mismatch`, `deduped`, `inventoried`. `mismatch` rows especially should be
   re-checked — a mismatch may have been fixed by a later recopy, and excluding them would
   strand rows that can never be promoted. `!= 'verified'` gets this right by construction;
   an allow-list of statuses would need maintaining every time one is added.
3. **Make the partial sweep loud.** This is the important one. `verify` today doubles as the
   archive's only bit-rot check; `--only-unverified` deliberately skips that. Print how many
   verified rows were skipped and when the disk was last fully verified (`verified_at` is
   already stored), so nobody mistakes an incremental pass for an integrity sweep. Same
   principle as the dedupe eligibility line — the fact that something was *not* checked has
   to be as visible as the result.
4. **Opt-in, never the default.** A bare `vault verify` keeps re-reading everything.
5. **Don't conflate it with a scrub schedule.** "Re-verify anything older than N days" is a
   genuinely useful second feature and a different one. Keep it out of this round.

## Notes for implementation

- `runVerify` currently hard-asserts `len(args) != 2`, so it needs real flag parsing —
  the smallest change that matches `parseScanFlags`'s style, not a new framework.
- F1's per-invocation hash cache is unaffected: filtering rows out only reduces what the
  cache is asked for. A `deduped` row whose destination is shared with an already-verified
  row will re-hash that destination — unavoidable, and trivial next to a full sweep.
- `inventoried` rows have an empty `dest_path` and `verify` falls back to `source_path`.
  `!= 'verified'` includes them, which matches what a full `verify` does today, so this
  changes nothing for that workflow.
- `certify` still requires every row `verified`, so an incremental pass is the fast route to
  a certifiable disk rather than a way around it. No change needed there.

## Done when

- `vault verify <disk> <dest> --only-unverified` hashes only non-verified rows.
- A bare `vault verify` still hashes everything.
- The output states how many verified rows were skipped and when the disk was last fully
  verified.
- A disk whose rows are all `copied` verifies identically under both modes.
- After an incremental pass promotes the last non-verified row, `certify` succeeds.
